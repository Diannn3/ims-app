2. SvelteKit + Supabase server architecture
I implemented the security boundary before multiplying academic screens.
Added:
src/hooks.server.ts src/app.d.ts src/lib/server/ ├── auth.ts └── supabase.ts
We now use a request-scoped Supabase SSR client, not a global server singleton.
Authentication flow:
Request ↓ hooks.server.ts ↓ request-scoped Supabase client ↓ getClaims() ↓ profiles.role ↓ SvelteKit locals ↓ protected route
This matches Supabase's current SSR direction: @supabase/ssr is the maintained SSR package, and verified claims/current-user checks should be used rather than trusting a cookie-loaded session object for authorization. ([npm](https://www.npmjs.com/package/%40supabase/ssr?utm_source=chatgpt.com))
I've also updated the runtime dependency lines to current releases available through the official npm registry, including current @supabase/ssr, supabase-js, and csv-parse. ([npm](https://www.npmjs.com/package/%40supabase/ssr?activeTab=dependencies&utm_source=chatgpt.com))
3. Staff authentication + RBAC
Implemented staff authentication:
/staff/sign-in /staff/sign-out
And protected:
/admin/*
Roles are modeled as:
student faculty content_editor map_editor admin
Important security decision:
authentication metadata does not decide someone's administrative role.
A database profile does.
I also added a database trigger that creates new authenticated users as:
role = student
by default.
No user can simply send:
{ "role": "admin" }
during signup and become an administrator.
4. Fixed the publication architecture
The earlier architecture mixed:
“Has this information been reviewed?”
with:
“Should students see it?”
I separated those concerns.
Institutional content now has a review concept:
draft needs_verification verified
while public exposure is controlled separately.
Critical invariant:
published ↓ MUST ALSO BE verified
So:
Verified but unpublished
is valid.
But:
Published but unverified
is rejected by database constraints.

6. Consultation ownership ≠ publishing authority
This is an important one.
A professor can eventually maintain their own consultation information, but cannot turn it directly into:

21. Transactional import apply
Implemented:
apply_import_batch(...)
The browser does not perform a series of mutation calls.
The database function:
checks admin ↓ locks batch ↓ checks ready ↓ checks zero errors ↓ checks preview hash ↓ checks warnings acknowledged ↓ applies everything ↓ writes provenance ↓ marks batch applied ↓ COMMIT
Failure anywhere rolls back the transaction.
22. Imported data fails closed
Another major rule:
Importing new/changed schedule information never automatically makes it public.
Instead:
CSV applied ↓ needs_verification ↓ human editor ↓ verified ↓ admin ↓ published
If a published schedule changes, the changed schedule is withdrawn until re-reviewed.
That's exactly the behavior we want for institutional information.
