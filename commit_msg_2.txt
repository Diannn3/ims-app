Public Data API boundary
I tightened the public architecture further.
Student-facing academic reads now go through things such as:
public_courses public_sections public_section_meetings public_faculty public_faculty_offices public_consultation_hours public_spaces public_academic_services ...
instead of the canonical moderation/import tables.
This matters because normal Postgres views are owner-executed by default and can bypass underlying RLS. Our architecture therefore deliberately uses explicit, fail-closed view predicates + explicit columns + revoked base-table access, rather than assuming RLS magically applies through the view. Supabase explicitly documents the default view behavior. ([Supabase](https://supabase.com/docs/guides/database/postgres/row-level-security))
I added database tests that verify the curated views retain security_barrier=true and remain owner-executed as intended.
Universal Search got hardened
I found one piece I didn't like in the previous implementation:
.or(`display_name.ilike.%${text}%,title.ilike.%${text}%`)
Even though we were sanitizing some characters, raw interpolation into PostgREST filter syntax is unnecessary.
That's gone.
Search now uses normal .ilike(column, value) query methods and merges the results.
Input also gets:
Unicode NFKC normalization whitespace normalization control-character removal LIKE wildcard removal: %, _, \ 80-character maximum
So something weird cannot turn into a giant wildcard directory scan or break raw filter grammar.
I also added tests for the normalization contract and put maxlength="80" on the UI search field.

Supabase environment safety got stronger
I hardened:
src/lib/server/supabase.ts
Hosted Supabase connections must now be:
https://...
while local development may still use:
http://127.0.0.1 http://localhost
More importantly, the application rejects:
sb_secret_...
if somebody accidentally places a modern Supabase secret key into a PUBLIC_* environment variable.
It also decodes legacy JWT-style keys and rejects:
role: service_role role: supabase_admin
A browser-adjacent configuration should only receive a publishable/legacy anon key.
Supabase is moving toward the newer publishable/secret key model and explicitly describes publishable keys as the client-side option. ([Supabase](https://supabase.com/docs/guides/api/creating-routes))
Our SvelteKit SSR architecture remains correct too: cookie-session SSR applications such as SvelteKit are a documented use case for @supabase/ssr, and getClaims() verifies the JWT before returning claims. ([Supabase](https://supabase.com/docs/guides/auth/choosing-a-server-package))
HTTP security boundary
I also hardened the SvelteKit response layer.
Responses now include:
X-Content-Type-Options: nosniff Referrer-Policy: strict-origin-when-cross-origin X-Frame-Options: DENY Content-Security-Policy: frame-ancestors 'none'; base-uri 'self'; object-src 'none';
frame-ancestors 'none' is the modern CSP protection against another site embedding the application for clickjacking. ([MDN Web Docs](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/frame-ancestors))
Unused powerful browser features are disabled for now:
camera microphone geolocation payment usb serial hid
We'll explicitly loosen those later only if a real feature needs them—for example, if we eventually decide to make an in-app QR scanner rather than letting students use their normal Camera app. Permissions Policy exists specifically to control access to these browser capabilities. ([MDN Web Docs](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Permissions_Policy))
Academic caching is now stricter
